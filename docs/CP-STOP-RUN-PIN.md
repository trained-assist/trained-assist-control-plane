# Immutable CP stop execution pins

Conversation stop snapshots retain receipt identity, the task generation at capture, and the complete sorted attempt set. Each attempt pins its CP attempt ID, canonical Runner ID (or unknown null), owner generation, and host-derived submission idempotency key. Retry uses the stored snapshot, never current activeRun discovery. Historical snapshots missing these fields remain unresolved and are not upgraded from current state.

The CP-owned pinned cancellation path atomically claims one fenced task generation with a durable snapshot/task correlation. Retries reuse that claim. SQL guards check the current snapshot, receipt, profile, task generation, exact attempt membership, Runner IDs and submission-key witnesses before claim, attempt finalization, proof publication and terminal mutation. Generation, run, key or membership drift stays unresolved. Runner cancellation always uses the captured canonical run and its captured owner generation; an overlapping new attempt is never substituted. A failure or race does not write a new task result or artifact, nor claim a fresh attempt exited.

Each Workflow generation uses a deterministic immutable instance ID derived from the task ID hash and generation. TaskStore records the instance ID in a generation-scoped event before create, so a retry after a process crash can discover the same handle. Signals, diagnostics, resume, credential readiness and recovery resolve the current generation's recorded handle. Legacy generations without a recorded handle continue to use the original task ID for compatibility.

Pinned Runner cancellation preserves the unresolved result unless the captured run's identity, owner generation, terminal status, and terminal result all agree. A failed confirmation adds a gateway Task Store error event at `cancel.pinned_external_stop` with an allowlisted `reasonCode` such as `cancel_runner_unavailable`, `status_connection_lost`, `status_nonterminal`, or `result_identity_mismatch`. Provider error text, response bodies, credentials, and input are never copied into this diagnostic. The user-visible stop remains unresolved; diagnostics do not authorize cleanup, restart, or mutation.

Pinned stop may inspect a legacy task-ID Workflow but never terminates through that mutable ID. For a generation with a persisted instance handle, it verifies the pinned snapshot/generation/attempt fence immediately before terminating that exact Workflow; success still requires observing that instance terminal. Native exit evidence alone does not confirm a still-running Workflow. Existing unpinned explicit cancellation remains unchanged. Offline tests are not live cancellation proof; sandbox3 acceptance is tracked in CP issue #240 and architecture scenario evidence.

## Remaining wire and ownership requirements

- Legacy tasks without a persisted generation handle are observed through `Workflow.get(taskId)` but are never terminated through it in the pinned path. If observation remains nonterminal, the stop remains unresolved until the matching Workflow exits through its own path or an operator reconciles it.
- Before the first snapshot exists, CP still discovers open conversation tasks when the admission barrier closes. A trusted intent-time task/receipt inventory or cutoff contract is needed to prove those memberships belonged to the original Telegram stop intent. A persisted snapshot never expands on retry.
- TG STOPfalse must gate mutations and pending stop alarms. This CP patch does not revoke old principals, change profile scopes, or isolate shared D1 from another authorized Worker. Direct legacy `/cancel` is outside the immutable conversation-window path.

Offline tests cover cold window retry, single generation claim, old snapshots, generation/attempt/run/key/profile drift, insertion between guard read and claim, insertion before native dispatch, a new native run during old cancellation, terminal SQL race, false exit provenance, and preserving later task identity and output ownership. No deployment, live control, owner credentials, or historical task rewrite is part of the change.

## Review follow-up

TaskStore `done`, `failed` or `cancelled` alone is never sufficient for pinned stop confirmation: execution-backed tasks require terminal Workflow observation, with errors or a running Workflow remaining unresolved. The narrow TaskStore-only quick-answer exception is described below. Already-finished execution status, timestamp, failure and result are immutable; successful native exit evidence can be recorded separately without turning a historical export failure into a successful attempt.

Cancellation status, awaiting closure, delivery suppression and the idempotent cancellation journal entry commit in one D1 transaction. A failed transaction rolls all four back; loss of its successful ACK leaves all four committed. Cold retry can repair historical cancelled rows with missing cleanup or journal, without duplicate events or changes to other terminal task results. Persisted confirmation for a snapshot is monotonic, and a stale snapshot cannot update its replacement. A fresh failed observation still returns unresolved: the stored confirmation bit is not used to bypass current Workflow or execution-pin checks.

Follow-up validation: the terminal-task/running-Workflow regression failed in all three terminal states before the fix. ## TaskStore-only quick answers

The known communication-v1 health/capabilities path commits a quick answer without creating an execution or Workflow. Its no-Workflow evidence requires a terminal `done` result, the exact saved deterministic routing selection and matching Output commit at the pinned generation, no attempts and no execution/submission witnesses. A missing Workflow is accepted only for that proven path and the exact runtime `instance.not_found` error. Arbitrary lookup failures, live Workflows, nonterminal tasks, historical executions and incomplete provenance remain unresolved.

CP output must be settled: `not_required` with no CP delivery rows, or `delivered` with acknowledged rows. Pending, accepted, failed or unknown delivery states hold the stop window. Snapshot confirmation also checks delivery state in SQL, preventing an enqueue between observation and confirmation from authorizing restart. No pending output is suppressed or resent by this quick-answer path. The observation does not attest to the external Telegram owner: its durable delivery gate still owns Telegram acknowledgement/unknown semantics before input release. No provider action is performed by these checks.

Late Runner receipt follow-up: a stop snapshot can capture the exact attempt after `runner_submit_started` but before submit returns, leaving its pinned `runId` null. CP now writes `runner_submit_receipt` as a durable event keyed by the captured CP attempt ID, containing the accepted task/profile/request identity, owner generation, idempotency key and canonical Runner ID. The snapshot remains unchanged; the stop path resolves that attempt through this witness, or for pre-fix tasks through the unique `run_started` receipt with the same attempt generation and idempotency key plus the exact submit-start witness. Both paths require the receipt run ID to equal the already attached `executions.session_id`; missing, malformed, ambiguous or conflicting evidence remains unresolved and cannot be replaced by mutable current-run discovery. Regression coverage proves new and legacy late binding through native stop, and refusal when the persisted idempotency key conflicts. Local typecheck and focused stop validation: 96 tests PASS across the stop-pin, stop-target and native-cancel suites. Full `npm run check`: 822 tests across 61 files PASS; evidence sanitizer PASS. This is offline evidence only and does not authorize sandbox3 deployment while its current Workflow remains nonterminal.

Submit/receipt race recovery: the stop path calls Runner's task-scoped cancel-by-idempotency-key contract for the exact attempt even when CP has no receipt. An authenticated `cancelled_before_admission` response is persisted as `preAdmissionCancellation` for the exact CP attempt, with `runId: null` and `exitObserved: false`; it proves the submit was fenced before admission. If Runner admitted that key, CP binds its returned run ID to the captured attempt. A matching authenticated terminal Runner status (`succeeded`, `failed`, or `cancelled`) is sufficient to prove the process is no longer active; `/result`, `exitObserved`, export, publication, and workspace cleanup remain separate facts. Missing key, task/generation mismatch, lost connection, unknown Runner state, or a nonterminal status stays unresolved and blocks replacement. New regressions cover the admission fence and terminal-status proof without waiting for result publication.

Unwitnessed submit recovery: an attempt with no persisted `runner_submit_started` marker and no Runner receipt is still fenced through the exact Runner idempotency key. This closes the narrow race where the external submit may have crossed the boundary before its witness was committed. A missing pinned Workflow is accepted only after Runner returns the identity-matched `cancelled_before_admission` fence for every attempt in the captured snapshot; an admitted run requires matching terminal Runner status. Any unknown/pending outcome stays unresolved. Ordinary duplicate submit now returns HTTP 409 for an unresolved same-generation `unknown`/`interrupted` attempt; a separately authorized explicit resume remains the path that advances generation. Regression tests cover no-witness fencing with a missing Workflow, status-only stop confirmation, and refusal to create another run after unknown.
