# M1, шаг 7 — Sandbox Web и сквозная приёмка

Web-срез первого сквозного диалога: тонкий клиент к API control plane, страница
одной conversation и воспроизводимый сквозной прогон с рестартом посередине.

Эпик: [trained-agent-architecture#109](https://github.com/trained-assist/trained-agent-architecture/issues/109),
шаг 7. Соседние шаги (2 и 4) живут в control plane; этот файл — только про web.

| `web/control-plane-client.ts` | HTTP-адаптер: приём, квитанция, журнал по курсору, сигнал, resume, байты артефакта |

## Принципы

1. **Источник истины — control plane.** Web держит только durable-индекс
   разговора (KV в Worker, память в тестах) и курсоры чтения. Вид разговора —
   чистая свёртка журнала, поэтому рестарт web или control plane не теряет и
   не перезапускает ничего: холодная сессия пересобирает вид с курсора 0.
2. **Ключи идемпотентности детерминированы от номера сообщения**
   (`web:<conversation>:m<N>`). Повтор отправки (двойной клик, F5, потерянный
   ответ) возвращает ту же квитанцию и тот же сигнал, а не новую задачу и не
   второе пробуждение.
3. **Никакого автоматического rerun.** Потеря связи — `unknown`, а не
   `failed` (P06); продолжение — только явным действием пользователя
   (`POST /web/conversations/:id/continue` → `POST /resume`, новый runId,
   generation+1).
4. **Журнал читается по курсору** (C02): `GET /events?after=<sequence>`,
   ответ — страница с `nextCursor`. Если в сборке control plane эндпоинта ещё
   нет (PR #7), клиент читает ту же таблицу событий из истории `/status` и
   помечает транспорт в отчёте (`transport: status-history`).
5. **Секреты — только env.** `CONTROL_PLANE_URL`, `CONTROL_PLANE_PRINCIPAL`,
   `CONTROL_PLANE_PROFILE`, `CONTROL_PLANE_API_KEY`. В репозитории, в логах и
   в отчётах ключ не появляется (проверено тестом).

## Сквозной сценарий (что именно проверяется)

Пять сообщений одной conversation:

```
m1 new     «собери сводку по песочнице»  -> приём (201) -> запуск -> awaiting_input
m2 answer  «только за вчера»             -> сигнал (ключ m2) -> done, результат
m3 new     «выгрузи результат в файл»    -> новая задача того же разговора -> awaiting_input
        *** РЕСТАРТ ПРОЦЕССА CONTROL PLANE ПОСЕРЕДИНЕ ***
m4 answer  «да, выгружай»                -> продолжение с курсора: тот же runId,
                                            run_started по-прежнему 1, done
m5 new     «итоговая сводка»             -> третий ход после восстановления
```

Проверки: квитанция выдаётся только после сохранения; повтор ключа возвращает прежнюю
квитанцию; ответ расходует ожидание ровно один раз; после рестарта попытка не
перезапускается; результат и ссылки на артефакты доступны после восстановления;
переподключение восстанавливает просмотр без потерь.

## Управляемые сбои

| Сбой | Где проверяется | Что обязан показать web |
|---|---|---|
| F1 оборванная доставка пробуждения (ответ сохранён, экземпляр не разбужен) | песочница, `tests/web-e2e-controlled-failure.test.ts` | повтор с тем же ключом доставляет сохранённый ответ ровно один раз; второй сигнал не создаётся |
| F2 рестарт процесса посреди ожидания | песочница + живой прогон | тот же runId, `run_started` не растёт, результат после восстановления |
| F3 потеря связи с исполнителем | песочница | попытка `unknown`, не `failed`; опрос не создаёт новую попытку; продолжение — явная новая попытка (новый runId, generation+1) |
| F4 потерянный HTTP-ответ после записи сигнала | песочница | повтор с тем же ключом не создаёт второй сигнал и не будит план дважды |

F1 и F4 — это ровно приёмка [#116](https://github.com/trained-assist/trained-agent-architecture/issues/116)
(«обрыв между сохранением wait и отправкой wake»): в живом API такой сбой
внедрить нельзя (нет хуков), поэтому он воспроизводится на песочнице, которая
реализует тот же контракт.

## Как запустить

```bash
npm ci
npm run typecheck
npm test                       # 73 теста, из них 22 — web-срез
```

Живой прогон против настоящего control plane (поднимает свой `wrangler dev`,
свою локальную D1, свой порт; рестарт процесса посреди разговора):

```bash
CONTROL_PLANE_REPO=../trained-assist-control-plane \
CONTROL_PLANE_PRINCIPAL=sandbox-local CONTROL_PLANE_PROFILE=profile-1 \
E2E_RESTART_MODE=process E2E_REPORT=docs/e2e/m1-step7-live-report.json \
node web/e2e/run-m1-web-slice-e2e.mjs
```

Или против уже поднятого control plane:

```bash
CONTROL_PLANE_URL=http://127.0.0.1:8787 CONTROL_PLANE_PRINCIPAL=sandbox-local \
CONTROL_PLANE_PROFILE=profile-1 E2E_RESTART_MODE=none node web/e2e/run-m1-web-slice-e2e.mjs
```

Страница разговора (отдельный Worker песочницы):

```bash
CONTROL_PLANE_URL=http://127.0.0.1:8787 CONTROL_PLANE_PRINCIPAL=sandbox-local \
CONTROL_PLANE_PROFILE=profile-1 npx wrangler dev -c web/wrangler.web.jsonc --port 8790
# открыть http://127.0.0.1:8790/web/conversations/<id>
```

## Известные ограничения (честно)

1. **Артефакты.** Настоящий план control plane не выпускает `artifactRefs`
   (`artifactRefsVisible: 0` в живом отчёте) — ссылки на артефакты появляются
   вместе с настоящим Runner (M1.3). Контракт и маршрут артефакта в web уже
   есть: байты проксируются с control plane, а если их источник недоступен,
   страница честно отдаёт `502` с причиной, а не выдумывает файл.
2. **Пятое сообщение остаётся в `awaiting_input`.** Настоящий план задаёт одно
   уточнение на ход, поэтому для терминального третьего хода нужен шестой
   (ответ) — сценарий проверяет пять сообщений и оставляет третий ход открытым,
   что само по себе является проверкой awaited input после восстановления.
3. **Деплой не выполнялся.** Песочница web-среза поднимается только локально;
   реальный деплой — по явной команде владельца (правила эпика).

## Что уже не ограничение

- **`/events` и `runs` в `/status`** (PR #7, смержен в main): живой отчёт
  идёт по основному пути `transport: events-endpoint`, `runId` виден через
  `/status` (таблица `executions`). Fallback на историю `/status` в клиенте
  остался на случай сборок без `/events` и покрыт тестом.
