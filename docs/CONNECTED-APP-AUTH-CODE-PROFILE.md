# First-party Connected App Authorization Code + PKCE profile

This opt-in code slice builds on [identity v1](../contracts/connected-app-identity-v1/README.md) and the [selected-profile authority gate](CONNECTED-APP-PROFILE-AUTHORITY-GATE.md). It follows the confidential BFF Authorization Code pattern in [RFC 10017 §6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1) and the code-flow protections in [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1). It is a closed first-party profile, not a complete general OAuth/OIDC authorization server: discovery metadata, dynamic client registration, consent UI and a production user-session authority are absent. No deployment or flag change is included.

The BFF starts an authorization transaction with a random `state` and a transaction-specific PKCE `code_verifier` stored **server side**. Its browser navigation to `GET /v1/connected-app-sessions/authorize` carries `response_type=code`, `client_id` (registered app audience), exact `redirect_uri`, space-separated `scope`, `state`, `code_challenge_method=S256` and `code_challenge=BASE64URL(SHA256(code_verifier))`. The authorization endpoint calls a typed `AgentProfileAuthority` port. On this branch, the opt-in implementation behind that port is still CP-hosted Telegram bootstrap prototype code, not the Agent producer runtime, and its D1 profile rows are not canonical Agent membership. The Worker makes the prototype available only when `CONNECTED_APP_TELEGRAM_BOOTSTRAP_ENABLED=true`; otherwise it returns 503. That flag is not configured in the deployed Worker. Any `profileId` parameter from the browser is ignored. Control Plane D1 stores the app-session projection, CP-local generation, and separate audience-specific app entitlements; it is not the Agent's canonical profile membership store.

The issuer stores only a SHA-256 hash of the random one-use code. The code is valid for 60 seconds and bound to client/audience, exact registered redirect, CP session generation, Agent profile generation, scopes, state hash and S256 challenge. The redirect carries `code`, `state` and `iss`, never an access token. The BFF verifies its stored state and expected issuer before calling `POST /v1/connected-app-sessions/exchange` as a confidential client with its audience-specific service credential. The form body contains `grant_type=authorization_code`, `client_id`, exact `redirect_uri`, `code`, `state` and `code_verifier`. Before consuming the code, the endpoint re-resolves the current Agent context. A changed/removed session rejects the exchange; an unavailable authority returns 503 without consuming the code. The app stores the opaque token server side, associates it with its own HttpOnly, Secure, SameSite cookie and calls no-store introspection for each protected request. Introspection returns inactive after Agent profile/session generation changes and a typed 503 if the Agent authority is unavailable.

Before activation, implement and bind the producer resolver in the Agent-owned runtime, review and privately provision its Telegram-to-principal and principal-to-profile crosswalk, configure exact HTTPS redirects and app credentials, deploy the reviewed migrations, and verify membership removal, profile switch, logout, code replay and authority outage with reviewed identities. Each Connected App still needs its own BFF callback/session store and CSRF review. Agent MCP delegation and cron service identity use separate host/service credentials and do not borrow this browser flow. The legacy web JWT or `web_current` cookie never becomes a trusted resolver.
