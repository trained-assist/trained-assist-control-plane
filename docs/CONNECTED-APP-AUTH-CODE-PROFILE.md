# First-party Connected App Authorization Code + PKCE profile

This opt-in code slice builds on [identity v1](../contracts/connected-app-identity-v1/README.md) and the [selected-profile authority gate](CONNECTED-APP-PROFILE-AUTHORITY-GATE.md). It follows the confidential BFF Authorization Code pattern in [RFC 10017 §6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1) and the code-flow protections in [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1). It is a closed first-party profile, not a complete general OAuth/OIDC authorization server: discovery metadata, dynamic client registration, consent UI and a production user-session authority are absent. No deployment or flag change is included.

The BFF starts an authorization transaction with a random `state` and a transaction-specific PKCE `code_verifier` stored **server side**. Its browser navigation to `GET /v1/connected-app-sessions/authorize` carries `response_type=code`, `client_id` (registered app audience), exact `redirect_uri`, space-separated `scope`, `state`, `code_challenge_method=S256` and `code_challenge=BASE64URL(SHA256(code_verifier))`. The authorization endpoint calls an injected `PlatformSessionResolver` to obtain the authenticated user, selected profile and grants. The production Worker supplies no resolver, so it returns 503 even if the general identity feature flag is enabled. Any `profileId` parameter from the browser is ignored. The selected binding and grant are kept in Control Plane D1; a profile/grant change advances its generation.

The issuer stores only a SHA-256 hash of the random one-use code. The code is valid for 60 seconds and bound to client/audience, exact registered redirect, selected session generation, scopes, state hash and S256 challenge. The redirect carries `code`, `state` and `iss`, never an access token. The BFF verifies its stored state and expected issuer before calling `POST /v1/connected-app-sessions/exchange` as a confidential client with its audience-specific service credential. The form body contains `grant_type=authorization_code`, `client_id`, exact `redirect_uri`, `code`, `state` and `code_verifier`. The endpoint checks the verifier and atomically consumes the code before issuing an opaque audience-bound token to the BFF. The app stores that token server side, associates it with its own HttpOnly, Secure, SameSite cookie and calls no-store introspection for each protected request.

To make this live, implement the real platform login/session resolver and BFF callback/session store; register exact HTTPS redirects and separate app credentials; establish CSRF defense on all cookie-authenticated BFF routes; publish metadata or an explicit supported profile document for clients; and prove switch, logout, grant removal, code replay and token revocation with two real profiles. Agent MCP delegation and cron service identity use separate host/service credentials and do not borrow this browser flow. The legacy web JWT or `web_current` cookie never becomes a trusted resolver.
