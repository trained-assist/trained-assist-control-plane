# Connected app identity v1

This is the control plane owned contract for profile identity at connected web applications. It is an **offline contract**, not a deployed token issuer or introspection route. A live integration must implement this contract only after the caller authentication and browser code exchange are designed and accepted. The retiring agent's web cookie, run token and machine secret do not implement it.

The control plane selects the current user and profile, grants explicit scopes for one audience, and issues an opaque token with at most a one hour lifetime. Only a registered app service may call introspection. Every introspection decision rechecks token, current session, selected profile, principal status and scopes. A profile switch, logout, revocation or removed scope returns `{ "active": false }` immediately; app responses and logs never contain the token. Consumers do not derive identity from query/body fields, arbitrary `x-profile` headers or the HH page cookie. A browser obtains its app credential through a one-time code exchange, never a URL token.

The app verifies the response's issuer, exact audience, times, current binding and requested operation scope before calling domain logic. `sub` is a platform user principal; `profileId` is the selected profile; `sessionId` identifies the authenticated browser or service session. A Task Run ID is only correlation and is neither an identity nor required for app use. A caller may get a subset of listed scopes. Recruiting R-01 needs `recruiting.responses.read` for response reading and `recruiting.assignment.review` for explicit review/save of vacancy assignment material; R-04 source read needs `recruiting.reports.read`, while private draft creation and internal review use separately named `recruiting.reports.create` and `recruiting.reports.review`; R-03's `recruiting.candidateSearch` is independent. CRM `crm.deals.create` is vocabulary for a separately gated deal-creation operation. Listing any write scope is only vocabulary: it creates no membership or grant, grants no human approval, and enables no production route. A selected profile needs a separately reviewed, enabled membership containing the exact scope. Any irreversible provider write additionally requires an independently trusted, one-use human-approval receipt; the app's own scope, cookie or form submission cannot mint one. Candidate messaging and client report delivery remain separate permissions and are not implied by these scopes.

The invented golden cases in `tests/connected-app-identity.contract.test.ts` check the contract shape, scope separation and dynamic invalidation. They do not prove a deployed issuer, live cryptography, browser handoff or real profile storage. The Recruiting consumer pins this contract by SHA and checks matching audience and scope vocabulary in its own CI.

The opt-in D1-backed host/service runtime in [`docs/CONNECTED-APP-IDENTITY-RUNTIME.md`](../../docs/CONNECTED-APP-IDENTITY-RUNTIME.md) implements the same response shape. It remains disabled by default and does not add browser handoff or a live selected-profile authority.
