# Connected app identity v1

This is the Control Plane-owned contract for identity at connected web applications. The Agent identity/profile authority authenticates the Agent user, owns user-to-profile membership and selected-profile lifecycle, and supplies verified profile context to the Connected App broker. Its producer contract is copied and SHA-pinned at [`contracts/agent-profile-context-v1/`](../agent-profile-context-v1/) from Agent revision `4a60c2e4c45eca9de1b84bba55e38bb83e1478c8`; CI checks the source hashes and typed CP port. The Agent artifact itself is contract-only, and the CP production Worker still has no resolver wired. The broker grants explicit app scopes for one audience and issues an opaque token with at most a one-hour lifetime. This remains an offline contract and opt-in runtime: the retiring Agent web cookie, run token, or machine secret does not implement it.

Only a registered app service may call introspection. Every introspection decision rechecks the token, current Agent session/profile generation, Agent membership, CP app entitlement and scopes. A profile switch, logout, revocation or removed scope returns `{ "active": false }`; an unavailable Agent authority returns a typed unavailable response and permits no protected operation. App responses and logs never contain the token. Consumers do not derive identity from query/body fields, arbitrary `x-profile` headers or the HH page cookie. A browser obtains its app credential through a one-time code exchange, never a URL token.

The app verifies issuer, exact audience, times, current Agent session/profile generation and requested scope before calling domain logic. `sub` is a platform user principal; `profileId` is the selected profile; `sessionId` identifies the authenticated session. A Task Run ID is only correlation. Recruiting R-01 needs `recruiting.responses.read` for list/status, the separate `recruiting.responses.conversation.open` for message-history reads that may mark a response viewed, and `recruiting.assignment.review` for explicit assignment review/save. R-04 source read, private draft creation and internal review use distinct `recruiting.reports.read`, `recruiting.reports.create` and `recruiting.reports.review`; R-03 search uses `recruiting.candidateSearch`. CRM catalog, deal status and deal creation use separate `crm.catalog.read`, `crm.deals.read` and `crm.deals.create`. A profile requires separately reviewed app membership for the exact scope. The create scope is vocabulary only: it grants no human approval and enables no production route. An irreversible provider write also requires an independently trusted, one-use operation-bound approval receipt. Candidate messaging and client report delivery remain separate permissions.

The invented golden cases in `tests/connected-app-identity.contract.test.ts` check the contract shape, scope separation and dynamic invalidation. They do not prove a deployed issuer, live cryptography, browser handoff or real profile storage. The Recruiting consumer pins this contract by SHA and checks matching audience and scope vocabulary in its own CI.

The opt-in D1-backed broker runtime in [`docs/CONNECTED-APP-IDENTITY-RUNTIME.md`](../../docs/CONNECTED-APP-IDENTITY-RUNTIME.md) implements the same response shape. Its `AgentProfileAuthority` port remains unbound in the production Worker, so it adds no live user login or profile authority.
