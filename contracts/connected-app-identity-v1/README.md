# Connected app identity v1

This is the control plane owned contract for profile identity at connected web applications. It is an **offline contract**, not a deployed token issuer or introspection route. A live integration must implement this contract only after the caller authentication and browser code exchange are designed and accepted. The retiring agent's web cookie, run token and machine secret do not implement it.

The Agent identity/profile authority authenticates the Agent user, owns user-to-profile membership and selected-profile lifecycle, and supplies verified profile context to the Connected App broker. The broker grants explicit app scopes for one audience and issues an opaque token with at most a one hour lifetime. Only a registered app service may call introspection. Every introspection decision rechecks the token, current Agent session/profile generation, Agent membership, CP app entitlement and scopes. A profile switch, logout, revocation or removed scope returns `{ "active": false }`; an unavailable Agent authority returns a typed unavailable response and permits no protected operation. App responses and logs never contain the token. Consumers do not derive identity from query/body fields, arbitrary `x-profile` headers or the HH page cookie. A browser obtains its app credential through a one-time code exchange, never a URL token.

The app verifies the response's issuer, exact audience, times, current binding and requested operation scope before calling domain logic. `sub` is a platform user principal; `profileId` is the selected profile; `sessionId` identifies the authenticated browser or service session. A Task Run ID is only correlation and is neither an identity nor required for app use. A caller may get a subset of listed scopes. Recruiting R-01 needs `recruiting.responses.read`; R-04 needs the distinct `recruiting.reports.read`, `recruiting.reports.create`, and `recruiting.reports.review` grants; vacancy assignment review needs `recruiting.assignment.review`; R-03's `recruiting.candidateSearch` is independent. CRM catalog, deal status, and deal creation use separate `crm.catalog.read`, `crm.deals.read`, and `crm.deals.create` grants. The create grant still requires the app's separate operation-bound approval receipt. Contract scopes do not enable production routes.

The invented golden cases in `tests/connected-app-identity.contract.test.ts` check the contract shape, scope separation and dynamic invalidation. They do not prove a deployed issuer, live cryptography, browser handoff or real profile storage. The Recruiting consumer pins this contract by SHA and checks matching audience and scope vocabulary in its own CI.

The opt-in D1-backed broker runtime in [`docs/CONNECTED-APP-IDENTITY-RUNTIME.md`](../../docs/CONNECTED-APP-IDENTITY-RUNTIME.md) implements the same response shape. Its `AgentProfileAuthority` port remains unbound in the production Worker, so it adds no live user login or profile authority.
